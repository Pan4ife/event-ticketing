## 1. Project Overview

Build a full-stack Events Ticket Booking Platform using React, Java Spring Boot, and PostgreSQL. The platform allows users to browse events, view event details, book tickets, manage their bookings, and receive personalized event recommendations. Event organizers or administrators can create and manage events, ticket availability, bookings, and event statuses.

The application should support real-world event types such as concerts, conferences, workshops, sports events, and meetups. Users should be able to search and filter events by category, date, location, price, and status. The platform must include authentication, role-based access control, pagination, validation, error handling, responsive UI, and API documentation.

Target users are regular customers who want to discover and book events, and admins/managers who manage events and platform data. The main value of the application is to provide a convenient and organized way to discover events, reserve tickets, and manage bookings in one place.

## 2. User Roles

Guest:
- Can view public event list and event details.
- Can search and filter events.
- Cannot book tickets.
- Cannot access dashboard, profile, or admin pages.

User:
- Can register, log in, and log out.
- Can view events and book available tickets.
- Can view booking history.
- Can cancel bookings if allowed by status rules.
- Can update personal profile data.
- Cannot create or edit events.
- Cannot manage other users.

Admin:
- Can manage users.
- Can create, update, publish, cancel, and delete events.
- Can view all bookings.
- Can update booking statuses according to the allowed status flow.
- Can access the dashboard with statistics.
- Can manage event categories.
- Can moderate event content and availability.

Optional Organizer role, if the student wants to extend the project:
- Can manage only own events.
- Cannot manage users.
- Cannot access global admin settings.

For the required implementation, Guest, User, and Admin are enough.

## 3. Core User Stories

- As a guest, I want to browse events, so that I can find interesting activities.

- As a user, I want to view event details, so that I can understand date, location, price, and availability.

- As an admin, I want to create and edit events, so that the platform has up-to-date event information.

- As an admin, I want to manage booking statuses, so that booking processing is controlled.
- As an admin, I want to view dashboard statistics, so that I can understand platform activity.
- As a user, I want to see recommended events, so that I can discover events matching my interests.
- As a user, I want to switch language, so that I can use the application comfortably.

## 4. Functional Requirements

### Authentication and Authorization

- Implement user registration with email, password, first name, and last name.
- Implement login with email and password.
- Implement logout on the frontend by removing the authentication token.
- Store passwords as hashes using BCrypt.
- Use JWT-based authentication.
- Protect private API endpoints with Spring Security.
- Implement role-based access control for User and Admin.
- Store user role in the database and include it in JWT claims.

### Main Business Entity Management

Main entities:
- Event
- Booking
- Ticket category
- Category
- User

Event management:
- Admin can create, update, delete, and change event status.
- Event must contain title, description, category, date/time, location, price, capacity, available tickets, image, and status.
- Users and guests can only view published events.
- Admin can view all events regardless of status.

Booking management:
- Authenticated users can create bookings for published events.
- Booking must reduce available ticket count.
- Users can view only their own bookings.
- Admin can view all bookings.
- Users can cancel their own booking only when cancellation is allowed.
- Admin can update booking status manually if needed.

### Search, Filtering, Sorting and Pagination

Event list must support:
- Pagination using page and limit.
- Total count in response.
- Sorting by date, price, newest, popularity, and status.
- Search by event title or description.
- Filtering by category, date range, price range, location, and event status.

Booking list must support:
- Pagination.
- Filtering by status.
- Sorting by created date or event date.
- For admin: filtering by user or event.

### Status Management

Event statuses:
- Draft

- Cancelled
- Archived

Booking statuses:
- Pending
- Confirmed

### Admin or Management Panel

Admin panel must include:
- User management page.

- Dashboard with key statistics.

Admin should be able to:
- View list of users.
- Block or activate users.
- View user bookings.

- View statistics such as total users, total bookings, upcoming events, revenue estimate, and sold tickets.

The project must include:

## 9. Status Flow

### Event Status Lifecycle

Available statuses:
- Draft
- Published
- Sold Out
- Completed
- Cancelled
- Archived

Valid transitions:
- Draft → Published
- Draft → Archived
- Published → Sold Out
- Published → Cancelled
- Published → Completed
- Sold Out → Published, if tickets become available after cancellation
- Sold Out → Completed
- Cancelled → Archived
- Completed → Archived

Who can change status:
- Admin can change all event statuses.
- System can automatically set status to Sold Out when availableTickets becomes 0.
- System can suggest Completed when event end date is in the past, but admin may confirm manually.

Invalid transitions:
- Cancelled → Published
- Completed → Published
- Archived → Published
- Archived → Draft

### Booking Status Lifecycle

Available statuses:
- Pending
- Confirmed
- Cancelled By User
- Cancelled By Admin
- Expired
- Attended

Valid transitions:
- Pending → Confirmed
- Pending → Expired
- Confirmed → Cancelled By User
- Confirmed → Cancelled By Admin
- Confirmed → Attended

Who can change status:
- User can cancel own confirmed booking before the event starts.
- Admin can confirm, cancel, expire, or mark attended.
- System can create booking as Confirmed immediately if payment is not implemented.

Invalid transitions:
- Cancelled booking cannot become Confirmed again.
- Attended booking cannot be cancelled.
- Expired booking cannot be confirmed.

## 11. Validation Rules

Authentication:
- Email is required and must be valid.
- Password is required and must be at least 8 characters.
- Email must be unique during registration.

Event:
- Title is required, 3–120 characters.
- Description is required, minimum 20 characters.
- Category is required.
- Start date must be in the future for new published events.
- End date must be after start date.
- Price must be zero or positive.
- Capacity must be greater than zero.
- Available tickets cannot exceed capacity.
- Image must be JPG, PNG, or WEBP and max 5 MB.

Booking:
- Event must exist and be published.
- Ticket quantity must be at least 1.
- Ticket quantity cannot exceed available tickets.
- User cannot book archived, cancelled, draft, completed, or sold out events.

Admin:
- User role and status updates must be valid enum values.
- Admin cannot block their own account.

## 12. Error Handling

Backend must return consistent errors:
- 400 for validation errors.
- 401 for missing or invalid token.
- 403 for forbidden access.
- 404 for missing resource.
- 409 for conflicts, such as duplicate email or insufficient tickets.
- 500 for unexpected server errors.

Frontend must:
- Show user-friendly messages.
- Show validation errors near form fields.
- Show global error notification for server errors.
- Redirect to login on 401.
- Show access denied page or message on 403.
- Not expose technical stack traces to users.
